# Codebase audit — November 7, 2026

## Coverage and method

Project Lead read the runtime integration: Villagers, Session, VillagerController,
AdventureActions, VillageSurvival, GodChildren, Speech, SocialReactions and both
mixins. Two bounded read-only reviewers covered every remaining Java source and
test, tooling scripts, build/resource configuration, pack-lock metadata, README,
and testing/training documentation. Design, architecture, coordination and retained
acceptance evidence were consulted. Generated Gradle infrastructure, dependency
binaries, release JAR internals, images, and every historical evidence JSON were
not independently audited. This is a complete application source read, not a
claim that every generated/binary artifact or gameplay path was verified.

The tree was already mostly untracked; preserve it. No existing runtime was
restarted or upgraded. Current source and historical running clients differ.

## Fixed during this audit

- Glossary saves retain the latest immutable snapshot until a successful write;
  transient failure can retry instead of silently discarding learned words.
- Rejoining players use pending progress instead of stale disk state.
- Glossary flush requests coalesce into one background job, rather than allowing
  an unbounded queue of snapshots; per-player errors are rate limited.
- Shutdown reports failure if changes remain unsaved.
- Fresh GlossaryStore instances inspect existing schema before saving, protecting
  future formats even when load was never called.
- The harvest intervention probe requires the isolated play role, protecting
  adaptive/frozen comparison worlds from injected tools and seeds.
- Explicit VILLAGERS_JAVA_HOME now verifies Java 25, matching other selection paths.
- README distinguishes current source from released artifacts and corrects its
  stale nonlethal-hunger and missing-language descriptions.

Four deterministic persistence regressions cover blocked-writer reconnect,
failed-write recovery, saving over a future format without loading, and failed
shutdown. Build verification is recorded in HANDOFF.md. These tests do not prove
in-game mixin compatibility, hunger pacing, speech usability, or survival.

## Open findings, ordered for follow-up

1. **Addressed in the subsequent restart-state pass (integration check pending).**
   TrainingTrial.Run previously reset its start tick and elapsed budget on construction.
   Restarting an accelerated world can grant another full budget, including after
   completion or a return to play. Persist terminal state and consumed ticks;
   require an explicit new experiment identity to reset them. Test restart
   boundaries before more accelerated experiments.
2. **Addressed in the evidence-writer pass (live failure check pending).**
   VillageTrial and LabClient previously had unbounded evidence queues. Coalesce
   replaceable reports, bound append-only work, and visibly stop accelerated work
   if evidence cannot keep up. Never silently label dropped evidence complete.
3. **Addressed by streaming asynchronous lookup (live/restart checks remain).**
   God-child ancestry selection previously called MindPersistence.census synchronously on the
   server thread. It reads every historical mind, so cost grows with lifetime
   deaths. Use an asynchronous lookup or maintained village ancestry index.
4. **Addressed in the evidence-writer pass (live cleanup check pending).**
   VillageTrial failure previously retained its chunk tickets until shutdown. Release
   owned tickets on terminal failure and test cleanup without touching others.
5. VillageTrial retains every historical actor and repeatedly copies the map into
   census output. Bound hot state and archive history separately; ensure markers
   cannot grow beyond their own restart-read limit.
6. prepare-client --refresh does not share the launcher runtime lock. Preparation
   can race another preparer or mutate a live directory. Reuse runtime exclusion.
7. Autonomous food supply is incomplete: wheat cannot become bread, real tools
   wear out, and no crafting replacement exists. Default starvation pacing is
   unvalidated. God children are recovery interventions, not survival successes;
   disable them in natural-cohort comparisons or record each intervention.
8. Speech has per-villager cooldowns, but automatic food requests/replies bypass
   them as prompted speech. Large villages may flood player chat. Add a bounded
   recipient budget and distinguish automatic conversation from player prompts.
9. Frozen controls differ in language/gossip/food-sharing behavior as well as
   learned action values. Define experimental axes explicitly before attributing
   survival differences to the action learner.
10. Several rare interactions and glossary joins still perform synchronous IO.
    Existing thinkNanos excludes door handling and equipment preparation. Measure
    whole-mod tick cost and disk stalls before expanding chunk residency.

## Architecture assessment

Keep the pure Java domain rules, bounded memories/opinions/lexicons, immutable
snapshots, world-scoped identities, atomic writes and future-schema protection.
Keep survival above elective learning and real item conservation in capabilities.
These are useful foundations for families and a conserved economy.

Avoid implementing all roadmap steps together. Each slice needs a deterministic
rule check, integration into the game, a visible isolated play check, and a
restart check where persistent state changes. A green build is a prerequisite;
positive gameplay evidence remains separate.

## Performance acceptance proposal

Before always-loaded villages or broad population growth, establish matched
visible-client baselines and incremental population runs. Record hardware, pack,
resident count, loaded chunks, actual TPS, p50/p95/p99 MSPT, mod time including
non-think hooks, path requests, IO backlog and memory. At normal 20 TPS the tick
budget is 50 ms; target p95 below this and explain outliers. No population capacity
claim is established by this audit. Use a bounded run and stop if evidence or
simulation cannot keep up. Increase populations only after the previous run is
healthy; avoid running multiple new clients merely for throughput.
